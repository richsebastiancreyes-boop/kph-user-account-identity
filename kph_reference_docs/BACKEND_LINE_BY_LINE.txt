 WHAT EACH FILE DOES AND WHAT IT IS FOR (read this before the details)
=====================================================================

Think of a restaurant. The API files (made by your groupmates) are the
WAITER: they take the order. The classes are the KITCHEN: they do the
real work. MySQL is the FRIDGE: it stores everything. Your part is the
kitchen plus the settings.

THE config/ FOLDER (settings and connection)

  config.php
    WHAT: one file with every setting: database login, secret key, how
          long codes last, the address limit, other modules' addresses.
    FOR:  so a setting is changed in ONE place and nowhere else.

  Database.php
    WHAT: opens the connection to MySQL using PDO.
    FOR:  every class shares this one connection. It is set up for safe
          queries (prepared statements) and to report errors.

THE classes/ FOLDER (the real work)

  Exceptions.php
    WHAT: two extra error types: AuthenticationException (wrong login)
          and ForbiddenException (not allowed).
    FOR:  so the API can turn each kind of error into the right status
          code (400, 401, 403, 404).

  Validator.php
    WHAT: a toolbox of input checks: name, email, phone, password, date,
          file address, and so on.
    FOR:  every rule is written once and used everywhere. Bad input is
          stopped before it reaches the database.

  Crypto.php
    WHAT: encrypts ID numbers (AES-256-GCM) and scrambles codes
          (HMAC-SHA256).
    FOR:  protecting private data. The database never holds a readable ID
          number or a readable code.

  Role.php
    WHAT: manages the `role` table: buyer, seller, admin.
    FOR:  making sure the 3 roles exist and looking them up.

  UserRole.php
    WHAT: manages the `user_role` table: who has which role.
    FOR:  giving and removing roles, with checks (no duplicates, an admin
          cannot remove their own admin role).

  AuthIdentity.php
    WHAT: manages the `auth_identity` table: the link between a user and
          a Google or Facebook account.
    FOR:  social login ("Continue with Google").

  VerificationToken.php
    WHAT: manages the `verification_token` table: one-time codes.
    FOR:  verifying an email or phone and resetting a password. A code
          works once, expires, and is saved only as a hash.

  UserProfile.php
    WHAT: manages the `user_profile` table: username, bio, picture,
          birthday.
    FOR:  the public side of a user. It also makes a username
          automatically and hides the birthday from other users.

  UserAddress.php
    WHAT: manages the `user_address` table: delivery addresses.
    FOR:  saving up to 10 addresses per user, with exactly one default.

  KycVerification.php
    WHAT: manages the `kyc_verification` table: the seller ID check.
    FOR:  a user sends an ID, an admin approves or rejects it. The ID
          number is encrypted and never returned.

  User.php   (THE MAIN CLASS)
    WHAT: manages the `user` table and uses all the classes above.
    FOR:  register, login, social login, edit account, change password,
          verify email or phone, reset password, suspend, reactivate,
          and the admin's user list.

  ModuleApi.php
    WHAT: sends requests to OTHER modules (notifications, logs).
    FOR:  connecting Module 1 to the rest of the system. It is switched
          OFF by default so Module 1 works alone.

THE RULE FOR ALL CLASSES
  Classes never print anything and never read the request. They return
  data or throw an error. The API files do the talking.

THE 10 PHP SYMBOLS YOU WILL SEE EVERYWHERE
  <?php            Starts PHP code.
  // text          A comment. PHP ignores it. It explains the code.
  $name            A variable (a box with a name that holds a value).
  [ ... ]          An array: a list, or a list of "name => value" pairs.
  "Key" => value   One pair inside an array, like "host" => "localhost".
  ->               "Use something that belongs to this object."
                   $this->db means "the db that belongs to this object".
  ::               "Use something that belongs to the class itself."
                   Validator::email(...) calls the email check.
  ??               "or this instead". $data["Email"] ?? null means:
                   use $data["Email"], or null if it was not sent.
  ?Type            "can also be null". ?array means "an array or null".
  throw new X(..)  Stops the method and sends an error to whoever called it.

A FEW MORE
  class            A blueprint. User is the blueprint for user actions.
  public/private   public = can be used from outside, private = only inside.
  static           Belongs to the class, you do not need to make an object.
  function         A named action (a method, when it is inside a class).
  : int, : array   The type of value the function gives back.
  require_once     Loads another PHP file, one time only.
  ===  !==         "exactly equal" and "not equal". Safer than == and !=.
  (string) (int)   Turn a value into text or into a whole number.
  prepare / execute  The two steps of a prepared statement (see below).

THE SAME 3 STEPS ARE IN ALMOST EVERY METHOD
  1) CHECK the input (with Validator).
  2) CHECK the rules in the database (is it taken? does it exist?).
  3) SAVE or READ, then RETURN the result. Or THROW an error.

PREPARED STATEMENT, THE PATTERN YOU WILL SEE 100 TIMES
      $stmt = $this->db->prepare("SELECT * FROM user WHERE UserID = ?");
      $stmt->execute([$userId]);
  The ? is a blank. The value is sent on its own in execute(). The
  database never mixes the user's text into the command, so SQL
  injection cannot work.
  SAY: "Every query in the backend uses a prepared statement. That means the
       SQL command is sent to the database first with blanks (the
       question marks), and the user's values are sent separately
       afterwards. Because of this, whatever the user types can never
       become part of the SQL command. This is how the backend is
       protected against SQL injection."

AFTER execute(), THESE APPEAR OFTEN
  fetch()          Get one row (an array), or false if there is none.
  fetchAll()       Get all rows.
  fetchColumn()    Get just the first value of the first row.
  lastInsertId()   The ID the database just gave to the new row.
  rowCount()       How many rows the last UPDATE/DELETE changed.
  "fetch() ?: null"  means: if there is no row, give back null.

WHAT "THROW" MEANS FOR THE API
  InvalidArgumentException  = wrong input or a broken rule  -> HTTP 400
  AuthenticationException   = wrong login                   -> HTTP 401
  ForbiddenException        = not allowed (suspended)       -> HTTP 403
  OutOfBoundsException      = not found                     -> HTTP 404
  anything else             = a real bug                    -> HTTP 500

 A2. WHAT IS PDO? (say this when you reach Database.php)
=====================================================================

WHAT IT IS
  PDO stands for PHP Data Objects. It is the tool that PHP uses to talk
  to a database. Our backend uses PDO to connect to MySQL, send queries,
  and read the answers back. Think of PDO as the phone line between the
  PHP code and the database.

WHY WE USE IT
  PDO supports prepared statements, which protect against SQL injection.
  It also reports database errors as exceptions, which our code can
  handle properly. And it works the same way for many databases, so the
  code does not depend on one specific database function.

HOW IT LOOKS IN OUR CODE
  1) Database.php creates the connection once:
        new PDO($dsn, $user, $password, $options)
     The $dsn is the address of the database: the type (mysql), the host,
     the database name and the character set (utf8mb4).
  2) Every class then uses that connection ($this->db) like this:
        $stmt = $this->db->prepare("SELECT * FROM user WHERE UserID = ?");
        $stmt->execute([$userId]);
        $row = $stmt->fetch();
     prepare() sends the SQL command with a blank (the ?). execute()
     sends the value separately. fetch() reads the answer.

THE THREE OPTIONS WE SET (Database.php lines 24-26)
  ERRMODE_EXCEPTION   If the database has an error, PHP throws an
                      exception. Without it, errors could be silent.
  FETCH_ASSOC         Each row comes back as an array with the column
                      names, like $row["Email"].
  EMULATE_PREPARES    Set to false. PHP does not pretend. It uses the
                      REAL prepared statements of MySQL, so the command
                      and the data really travel separately.

WHAT A PREPARED STATEMENT IS
  A prepared statement is a SQL command with blanks for the values. The
  database receives and understands the command first. Only then does it
  receive the values, and it treats them as plain data, never as part of
  the command. So if someone types ' OR '1'='1 as their email, the
  database just looks for a user whose email is literally that text, and
  finds nobody.

SAY: "PDO is the way our PHP code connects to MySQL. We use it because it
      supports prepared statements, which keep user input separate from
      the SQL command, so SQL injection cannot work. Our Database class
      opens one PDO connection and every class shares it. We also set it
      to throw exceptions on errors and to use real prepared statements."

 5. classes/Crypto.php   (43 lines)
=====================================================================

WHAT THIS FILE IS
  Two jobs: ENCRYPT an ID number so it can be read back only with the
  secret key, and SCRAMBLE tokens (codes) in a one-way way.

LINE 5      require_once Database.php: to read the key from config.

LINES 9-16  key()  (private: only used inside this class)
  Line 11: read "encryption_key" from the settings.
  Line 12: ctype_xdigit checks it only has 0-9 and a-f, and strlen must
           be 64. If not, throw "must be 64 hex characters".
  Line 15: hex2bin turns the 64 characters into 32 raw bytes, which is
           the size AES-256 needs.

LINES 18-25 encrypt($plain)
  Line 21: random_bytes(12): a new random 12-byte "IV" every time. This
           is why encrypting the same ID number twice gives different
           results.
  Line 22: $tag will receive an "authentication tag" (16 bytes). It is a
           seal that lets us notice if someone changed the data.
  Line 23: openssl_encrypt(...) with "aes-256-gcm" does the encryption.
  Line 24: join IV + tag + encrypted data and base64_encode it into plain
           text that fits in a VARCHAR column.
  SAY: "The ID number is encrypted with AES-256-GCM, which is a strong, modern
       encryption method. Every time, a new random value called the IV
       is made, so the same ID number never gives the same result twice.
       The saved text holds the IV, an authentication tag and the
       encrypted data, joined together and turned into base64 text. The
       tag lets us notice if somebody changed the data, because then
       decryption fails."

LINES 27-36 decrypt($stored)
  Only for server-side checks. The API never returns it.
  Line 30: base64_decode back to raw bytes.
  Lines 31-33: if it is not valid or too short (under 29 bytes = 12 + 16
           + at least 1), return null.
  Line 34: split the bytes: the first 12 are the IV, the next 16 are the
           tag, the rest (from byte 28) is the encrypted data. Then
           openssl_decrypt.
  Line 35: if decryption fails (wrong key, or data changed), return null
           instead of an error.

LINES 38-42 hashToken($token)
  hash_hmac("sha256", $token, key) scrambles a token ONE WAY with the
  secret key. The same token always gives the same result, so we can
  search for it in the database, but nobody can turn it back into the
  token.
  SAY: "Encryption can be reversed with the key, but hashing cannot be reversed
       at all. We encrypt ID numbers because the system may need to read
       them again later. We hash the codes because we only ever need to
       check them, never read them. So even if someone steals the
       database, they cannot read the codes, and they cannot read the ID
       numbers without the secret key."

IN ONE BREATH:
  SAY: "Register checks every field, checks that the email and phone are free,
       and hashes the password. Then, in one transaction, it creates the
       user, the profile and the buyer role. Either all three are saved
       or none. Finally, it returns the new UserID to whoever called

IF ASKED "WHAT IF IT FAILS HALFWAY?"

       has no explicit rollBack line. MySQL discards the unfinished work
       when the request ends and the connection closes."

=====================================================================
 15. HONEST NOTES (say these first if the professor pokes)
=====================================================================

  - TRANSACTIONS: used in register, social login, address create /
    update / delete, and token create. There is no explicit rollBack
    line. If something fails before commit(), the database drops the
    unfinished work when the request ends.
  - LOGIN MESSAGE: one generic message for unknown email, no password
    and wrong password. The "suspended" message only shows after the
    password is correct.
  - PASSWORD LIMIT: maximum 72 characters. That is a limit of the
    hashing method.
  - SINGLE USE CODES: a code works once, expires (30 / 10 / 30 minutes
    from config), and a newer code cancels older ones.
  - show_token_in_response = true is DEMO MODE. A real system would
    send the code by email or SMS. Set it to false for the final demo.
  - ModuleApi is OFF by default. Other modules are not ready.
  - SOCIAL LOGIN IS SIMULATED: User.php lines 96-97 say a real system
    must first ask Google/Facebook if the token is real. KameraPH
    pretends to be the provider, so the data sent in is trusted.
  - ENCRYPTION KEY: everyone should use their own and not change it
    later, or old encrypted ID numbers cannot be read.
  - PhoneNumber is not unique in the database, only in the code. Email is
    unique in the database.
  - The backend has no pages. The API files (waiter) call the classes
    (kitchen), and the classes talk to MySQL (fridge). The API and the
    frontend are done by other groupmates.
